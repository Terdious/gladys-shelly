# Gladys Shelly — external integration

Connect your **Shelly** devices to [Gladys Assistant](https://gladysassistant.com):
relays, smart plugs, energy meters, roller shutters, dimmers and colour lights,
inputs and buttons — with dashboard widgets, scene triggers and actions, and a
built-in diagnostic.

Built on [`@gladysassistant/integration-sdk`](https://github.com/GladysAssistant/integration-sdk-js)
following the [official integration template](https://github.com/GladysAssistant/integration-template-js):
a standalone Docker container that talks to the Gladys core over an outbound
WebSocket + REST. No HTTP server, no custom UI — the configuration screen is
generated by Gladys from the manifest `config_schema`.

## What it does

- **Local first, in real time.** Speaks the Shelly **Gen2+ RPC protocol**
  directly to your devices on your LAN, over a **WebSocket the device pushes
  to**: a relay flipped on the wall shows up in about a second, not at the next
  poll. A fully local setup needs an **empty configuration form**: no account,
  no MQTT broker, no cloud.
- **Cloud as a fallback.** When a device is unreachable locally, the integration
  can route through the **Shelly Cloud** — and says so, per device, with a
  transport badge.
- **Finds your devices for you.** Core-mediated **mDNS** discovery
  (`_shelly._tcp`), merged with hand-typed addresses for devices on another VLAN
  and with the addresses of the devices already created.
- **Maps what the device actually has.** Feature sets are derived from the
  components in `Shelly.GetStatus` — not from a hard-coded model table. A Shelly
  Pro 1 gets an On/Off, a Pro 1PM gets metering too, and a model released after
  this code still works.

### Supported today

| Shelly component               | Gladys features                                                                         |
| ------------------------------ | --------------------------------------------------------------------------------------- |
| `switch:N`                     | On/Off (writable), power, voltage, current, total energy, internal temperature          |
| `cover:N`                      | Shutter state and position (writable, position once calibrated), metering               |
| `light:N` / `rgb:N` / `rgbw:N` | Light on/off, brightness, colour (writable), power                                      |
| `cct:N`                        | Light on/off, brightness, colour temperature (writable), power                          |
| `input:N`                      | Input (switch mode), button + scene trigger (button mode), counter (count mode)         |
| `em:N`                         | Per-phase (L1/L2/L3) active & apparent power, voltage, current; totals; neutral current |
| `emdata:N`                     | Total and returned energy, per phase and total                                          |
| `em1:N` / `em1data:N`          | Single-phase meter equivalents                                                          |
| `pm1:N`                        | Standalone power meter                                                                  |
| `temperature:N`, `humidity:N`  | Temperature, humidity                                                                   |
| `devicepower:N`                | Battery level                                                                           |

Designed against real payloads from a **Shelly Pro 3EM**, a **Shelly Pro 4PM**,
a **Shelly Pro 3**, a **Shelly Plus 2PM**, a **Shelly Plus Plug S** and a **Gen1
3EM**; covers, lights and inputs follow the documented API and wait for bench
reports.

On top of the devices (Gladys 5.1+):

- **Dashboard widgets**: energy meter, switches (All on / All off), shutters
  (Open / Stop / Close / Position for a group), network health.
- **Scene triggers**: button pressed (single / double / triple / long),
  reachability changed. **Scene actions**: turn on for a duration (timer kept
  by the device), restart a Shelly.
- **Diagnostic** buttons on the Configuration screen: a masked report of the
  whole fleet, and a live, read-only test of one device by its IP.
- **Four languages** (en, fr, de, es) for every text, the documentation, and
  optionally the feature names of new devices.

**Generations:** Gen2 and later (Plus, Pro, Mini, Gen3, Gen4) **and Gen1**
(Shelly 1, 1PM, 2.5, Plug S, EM, 3EM). Gen1 speaks a completely different API —
REST instead of JSON-RPC, Basic auth instead of Digest — but it is normalized
into the same component model, so a Gen1 3EM exposes exactly the same features
as a Gen2 Pro 3EM. Gen1 has no real-time channel reachable from a container
(CoIoT is multicast), so those devices follow the refresh interval, unless they
publish to MQTT.

## Installation

In Gladys: **Integrations → Install an integration → Shelly → Install**, then
**Discovery → Scan**.

Everything else — including the fact that you probably have nothing to fill in —
is covered in the [user documentation](./docs/en.md).

## Configuration

Every field is optional. A local-only install works with all of them empty.

| Key                 | Type      | What it is                                                         |
| ------------------- | --------- | ------------------------------------------------------------------ |
| `manual_hosts`      | `string`  | Comma-separated IPs/hostnames for devices mDNS cannot see          |
| `device_username`   | `string`  | Device username — always `admin` on Gen2+                          |
| `device_password`   | `secret`  | Device password, when authentication is enabled on the devices     |
| `cloud_enabled`     | `boolean` | Turn on the Shelly Cloud fallback                                  |
| `cloud_server`      | `string`  | Account server, e.g. `shelly-53-eu.shelly.cloud`                   |
| `cloud_auth_key`    | `secret`  | Shelly Cloud authorization key                                     |
| `feature_names`     | `select`  | Language of the feature names of new devices (en/fr/de/es)         |
| `refresh_interval`  | `select`  | Poll cadence in seconds (10 / 30 / 60 / 300), default 30           |
| `realtime_interval` | `select`  | Real-time lane cadence (1 / 5 / 10 / 30 s, or disabled), default 5 |

The manifest declares `transports: ["local", "cloud"]`, so Gladys renders its
own **"Prefer the local connection"** toggle and hands it to the integration as
the reserved `GLADYS_PREFER_LOCAL` key.

## Project structure

```
index.js                     SDK wiring only — no Shelly logic
src/
  config.js                  form values -> typed, defaulted configuration (DEFAULT_CONFIG)
  actions.js                 Configuration screen buttons: fleet diagnostic, device test
  diagnostic.js              report formatting and redaction (no secret, masked ids)
  scenes.js                  scene actions: turn on for a duration, restart
  widgets.js                 dashboard widgets: energy meter, switches, shutters, network
  shelly/
    constants.js             component vocabulary, timeouts, UI messages (en/fr/de/es)
    rpc.js                   Gen2+ JSON-RPC over HTTP + SHA-256 digest auth
    cloudClient.js           Shelly Cloud Control API client
    client.js                transport router: local, MQTT, cloud fallback, badges
    commands.js              Gladys value -> Shelly command, spelled for RPC, Gen1 and cloud
    localCircuit.js          per-device breaker: stop retrying a dead device every cycle
    wsRpc.js                 real-time RPC over WebSocket (in-payload digest auth)
    wsHub.js                 one push connection per device, declaratively synced
    mqttHub.js               MQTT transport, inventory and push (Gen2+ RPC and Gen1 topics)
    selector.js              derived, reconstructible device and feature selectors
    discovery.js             mDNS + MQTT + manual + known hosts -> probed devices
    features.js              component -> feature specs (ONE table, both directions)
    featureNames.js          feature names in en/fr/de/es
    deviceMapping.js         device model and status -> states
    telemetry.js             refresh loop, real-time lane, events, triggers, dedup
    setValue.js              command routing
    gen1/                    Gen1 REST client and normalization into the Gen2+ model
    async.js                 bounded-concurrency map
test/
  helpers/fakeShelly.js      real HTTP + WebSocket server emulating a Shelly
  helpers/fakeGladysCore.js  fake core (REST + WebSocket) for the e2e test
  manifest.test.js           manifest <-> code: defaults, handlers, languages, versions
  release.test.js            release helpers against the real manifest and changelog
.github/scripts/release.mjs  manifest bump and changelog roll of the Release workflow
```

The key design point is `src/shelly/features.js`: **one table** describes each
feature _and_ how to read its value from a status payload. Discovery and
telemetry both consume it, which structurally prevents the classic drift where a
feature is published but never fed.

The second one is `src/shelly/selector.js`. Gladys selectors are unique across
the whole installation, and derived from the display name when discovery omits
them — so two devices each exposing an unnamed relay collide and the second is
rejected. Selectors here are always explicit and always **derived** from the
Shelly id plus the component key: unique by construction, and reproduced
identically on every re-discovery so an update never creates a duplicate.

## Development

```bash
npm install
npm test            # node --test: 241 tests, no network needed
npm run lint
npm run format:check
```

Run it against a real Gladys core without Docker:

```bash
GLADYS_HOST_API_URL=http://192.168.1.10:1080 \
GLADYS_INTEGRATION_TOKEN=<integration jwt> \
GLADYS_INTEGRATION_SELECTOR=shelly \
LOG_LEVEL=debug \
npm start
```

Releases go through **Actions → Release** → pick patch / minor / major: it
bumps `package.json` and the manifest in lockstep, moves the `[Unreleased]`
section of [CHANGELOG.md](./CHANGELOG.md) under the version, tags `vX.Y.Z`,
publishes the multi-arch image (`:X.Y.Z` and `:latest`) and the **GitHub
Release** whose notes are that changelog section (the Gladys Supervision page
links to it). Never edit the versions by hand; describe every user-visible
change under `## [Unreleased]` as you make it.

Check the manifest against the store admission rules with
`npx github:GladysAssistant/integration-store .`.
